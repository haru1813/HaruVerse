WHY — Gradle을 고른 이유
  • 의존성 선언이 간결 — Maven은 XML 5줄, Gradle은 1줄
    implementation 'org.springframework.boot:spring-boot-starter-web'
  • 빌드가 빠름 — 증분 빌드 + 빌드 캐시 (↓ 아래에서 상세)
  • 신규 프로젝트 표준 — Maven은 레거시·전통 기업 쪽에 많이 남아있는 편
  • Gradle wrapper(gradlew) 포함 → 팀원이 Gradle을 따로 설치할 필요 없음, 버전도 통일됨

📌 "빌드가 빠르다"의 실체 — 증분 빌드 & 빌드 캐시

① 증분 빌드 (Incremental Build) — "바뀐 것만 다시"

안 바뀐 건 건너뛰고, 바뀐 것만 다시 빌드한다.

파일 100개 중 1개만 수정 시MavenGradle
동작100개 전부 재컴파일바뀐 1개만
체감약 30초약 2초

어떻게 아느냐: Gradle이 각 파일의 지문(해시)을 기록해둔다. 다음 빌드 때 "지문이 그대로면 결과물도 그대로"라고 판단 → 그 작업을 통째로 건너뜀.

> Task :compileJava UP-TO-DATE   ← 바뀐 게 없어서 아예 실행 안 함
② 빌드 캐시 (Build Cache) — "예전에 한 결과를 꺼내 씀"

과거 빌드 결과물을 보관했다가, 같은 입력이면 다시 만들지 않고 꺼내 쓴다.

증분 빌드빌드 캐시
비교 범위이번 빌드 vs 직전 빌드과거 모든 빌드 결과 보관
판단"방금 뭐 바뀌었지?""이거 예전에 해봤나?"

차이가 드러나는 예:

1. 코드 A → 빌드 (30초)  → 결과를 캐시에 저장
2. 코드 B로 변경 → 빌드 (30초)
3. 다시 코드 A로 되돌림 → 빌드 0초 (캐시에서 꺼냄)
   ↑ 증분 빌드는 여기서 다시 빌드함 (직전이 B였으니까)
     빌드 캐시는 "A 해본 적 있네?" 하고 꺼내줌

특히 강력한 곳: 브랜치 전환(갔다 돌아와도 캐시 적중) · 팀/CI 공유 캐시(동료나 CI가 빌드한 결과를 내가 받아 씀)

WHY — Maven은 왜 이게 안 되나 (구조적 차이)
  • Maven은 각 작업의 입력·출력이 무엇인지 명확히 모르는 구조 → "안 바뀐 걸 어떻게 확신하나"를 판단하기 어려움 → 그냥 다 다시 하는 게 안전
    (mvn clean install이 관례처럼 쓰이는 이유 — 아예 지우고 새로)
  • Gradle은 각 작업의 입력·출력을 명확히 선언하는 구조 → "입력이 같으면 출력도 같다"고 확신 가능 → 건너뛰기·캐싱이 성립
⚠️ 헷갈리지 말 것 — Gradle 빌드 캐시 ≠ Docker 레이어 캐싱
Gradle 빌드 캐시Docker 레이어 캐싱
주체GradleDocker
캐시 대상자바 컴파일 결과이미지 레이어
위치~/.gradleDocker 데몬

둘 다 "안 바뀐 건 재사용"이라는 원리는 같지만 층이 다르다. Dockerfile에서 의존성을 먼저 COPY한 건 Docker 레이어 캐싱 이야기(02번 항목), 여기는 Gradle이 자바를 컴파일할 때 이야기.

지금은 체감 안 되지만 — 나중에 효과를 본다
현재 파일 3개라 차이가 없다. 그러나 work·member·auth·favorite·search 도메인이 쌓여 파일이 수십~수백 개가 되면 → 컨트롤러 하나 고칠 때마다 30초 vs 2초의 차이가 된다. 지금 Gradle을 고른 판단이 그때 회수된다.

📌 Gradle Wrapper — "Gradle을 설치하지 않아도 되는 이유"

사실 확인 — 이 PC엔 Gradle이 설치돼 있지 않다
$ which gradle
→ 없음 (설치 안 됨)

$ ./gradlew bootRun
→ 정상 빌드·실행됨   ← 어떻게?
Wrapper가 Gradle을 대신 받아와서 실행했기 때문.
구성 파일 4개
파일역할
gradlew실행 스크립트 (Mac/Linux)
gradlew.bat실행 스크립트 (Windows)
gradle/wrapper/gradle-wrapper.jar실제 동작하는 작은 프로그램
gradle/wrapper/gradle-wrapper.properties 어떤 Gradle 버전을 쓸지 적힌 파일 ⭐
# 이 프로젝트의 gradle-wrapper.properties
distributionUrl=https\://services.gradle.org/distributions/gradle-9.5.1-bin.zip
                                                            ↑ 9.5.1을 쓰겠다고 박제
./gradlew 실행 시 벌어지는 일
① ./gradlew 실행
     ↓
② gradle-wrapper.properties 읽음  → "9.5.1 쓰라고 하네"
     ↓
③ ~/.gradle 에 9.5.1이 있나?
     ├─ 없으면 → 인터넷에서 자동 다운로드  ← 첫 실행이 오래 걸린 이유
     └─ 있으면 → 그대로 사용
     ↓
④ 받아온 Gradle 9.5.1로 실제 빌드
WHY — Wrapper가 필요한 진짜 이유 (설치 편의보다 중요)

Wrapper가 없으면 — 팀원이 각자 Gradle을 설치한다.

  • A는 8.5, B는 9.5, CI 서버는 7.0... 버전이 제각각
  • 버전마다 문법·동작이 미묘하게 달라 빌드가 깨진다
  • → "내 컴퓨터에선 되는데?" 지옥

Wrapper가 있으면

  • 버전이 gradle-wrapper.properties에 박제되어 git으로 함께 공유됨
  • → 내 PC · 동료 PC · CI 서버 · Docker 컨테이너 — 어디서 빌드하든 무조건 9.5.1
  • → 환경 차이로 인한 빌드 문제가 구조적으로 사라진다

즉 Wrapper의 본질은 "설치 안 해도 됨"이 아니라 "버전을 강제로 통일함"이다.

그래서 지켜야 할 규칙 3가지
항목규칙
명령어gradle build ❌ → ./gradlew build ⭕ (항상 wrapper 경유)
gitwrapper 파일 4개를 전부 커밋 — 안 하면 clone 받은 사람이 wrapper를 못 씀
버전 변경properties를 손으로 고치지 말고 → ./gradlew wrapper --gradle-version 9.6

.gitignore를 보면 근거가 보인다:

.gradle
build/
!gradle/wrapper/gradle-wrapper.jar   ← "이건 예외로 반드시 커밋해라"

보통 .jar는 git에 넣지 않지만, wrapper jar만은 필수로 커밋해야 하므로 !(예외)로 지정돼 있다.

Dockerfile에서도 같은 원리를 썼다
COPY gradlew .
COPY gradle gradle          ← wrapper 폴더
RUN ./gradlew bootJar
Docker 이미지에도 Gradle을 설치하지 않았다. wrapper가 알아서 받아오게 했다. → 로컬이든 컨테이너든 동일한 Gradle 버전으로 빌드된다.
한 줄 비유
Wrapper = 이 프로젝트 전용 Gradle 자판기.
프로젝트에 자판기가 붙어 있고, 버튼(./gradlew)을 누르면 정해진 버전(9.5.1)이 나온다. 누가 눌러도 같은 게 나온다 — 그게 핵심.
WHY — application.yml을 고른 이유
  • properties는 접두어를 계속 반복한다 — spring.datasource.url, spring.datasource.username...
  • yml은 계층 구조라 설정이 늘어날수록(DB·JPA·보안) 가독성 차이가 커짐
  • 프로파일 분리(dev/prod)를 한 파일에서 --- 로 처리 가능
  • 단점: 들여쓰기 실수에 취약 (탭 금지, 스페이스만)

02Dockerfile — multi-stage로 작성

# 1단계: JDK로 빌드
FROM eclipse-temurin:21-jdk-alpine AS build
WORKDIR /app
COPY gradlew . ; COPY gradle gradle
COPY build.gradle settings.gradle ./
RUN ./gradlew dependencies --no-daemon   ← 의존성 먼저 (캐싱)
COPY src src
RUN ./gradlew bootJar --no-daemon

# 2단계: JRE로 실행
FROM eclipse-temurin:21-jre-alpine          ← JDK 아니라 JRE
RUN addgroup -S spring && adduser -S spring -G spring
USER spring                                ← root로 안 돌림
COPY --from=build /app/build/libs/*.jar app.jar
EXPOSE 8082
ENTRYPOINT ["java", "-jar", "app.jar"]
WHY — 설계 판단 4가지
설계이유
multi-stage JDK는 빌드할 때만 필요하다. 최종 이미지에 JDK를 넣으면 불필요하게 무거워지므로, 결과물(jar)만 JRE 이미지로 복사한다 → 이미지 크기 대폭 감소
의존성을 소스보다
먼저 COPY		 Docker는 레이어 단위로 캐싱하고, 바뀐 레이어부터 다시 빌드한다.
소스는 자주 바뀌고 의존성은 잘 안 바뀌므로 → 의존성을 위쪽에 두면 소스만 고쳤을 때 의존성 재다운로드를 건너뜀
JRE + alpine 실행에는 컴파일러(JDK)가 불필요 + alpine은 경량 베이스
USER spring root로 컨테이너를 돌리지 않는다. 컨테이너가 탈취돼도 권한을 최소화 (보안 기본 원칙)

03docker-compose — 왜 Dockerfile을 안 쓰고 image:를 썼나 ⭐

Q. Dockerfile로 이미지를 만들고, compose가 그 이미지를 컨테이너로 띄우는 것 아닌가?

맞다. 다만 Compose는 두 가지 방식을 모두 지원하고, 개발 단계에서는 다른 쪽을 골랐다.

방식동작쓰는 곳
build: ./backend 내 Dockerfile로 이미지를 빌드해서 컨테이너로 배포용 이미지를 만들 때
image: eclipse-temurin 이미 있는 이미지를 받아서 컨테이너로 개발 (← 채택)
WHY — 개발 compose에서 image + 볼륨 마운트를 고른 이유
  • build:를 쓰면 → 소스를 한 줄 고칠 때마다 이미지를 다시 구워야 한다 (수 분) → 개발 사이클이 너무 느림
  • image:(JDK 깡통) + 소스 볼륨 마운트 → 재빌드 없이 즉시 반영
  • 즉 "이미지 안에 소스를 굽는" 게 아니라 "JDK 깡통에 소스를 꽂아서" 돌리는 구조
  • 기존 frontend가 이미 이 패턴이었다 → 백엔드도 동일하게 맞춤 (일관성)
    • frontend/Dockerfile = 프로덕션(nginx 정적 서빙)
    • compose의 frontend = image: node:20-alpine + 마운트 + npm run dev
그럼 Dockerfile은 언제 쓰나

나중에 k3s·ArgoCD로 배포할 때 쓴다.

docker build -t haruverse-backend ./backend   # Dockerfile → 이미지
docker push ...                               # 레지스트리에 등록
# → k8s가 그 이미지를 받아 배포

즉 Dockerfile = 배포용 / compose = 개발용으로 역할이 나뉜다. 추후 docker-compose.prod.yml을 따로 두는 방식(개발/배포 파일 분리)도 실무에서 흔함.

gradle-cache 볼륨을 만든 이유
volumes:
  - gradle-cache:/root/.gradle
이게 없으면 컨테이너를 재시작할 때마다 의존성을 전부 다시 다운로드한다(수 분). 볼륨에 캐시해두면 두 번째 실행부터 빠르다.

04트러블슈팅 — 오늘 막힌 것들

① Initializr 버전 ID ≠ Maven 실제 버전 (핵심 삽질)
  • 증상: Could not find artifact spring-boot-starter-parent:pom:4.1.0.RELEASE → 빌드 실패
  • 원인: Initializr 메타데이터의 버전 ID는 4.1.0.RELEASE인데, Maven Central의 실제 아티팩트는 4.1.0. ID를 그대로 넘겨서 404.
  • 확인 방법: 저장소 URL에 직접 요청해서 존재 여부 확인 
    curl -o /dev/null -w "%{http_code}" \
  https://repo.maven.apache.org/maven2/org/springframework/boot/\
spring-boot-starter-parent/4.1.0/spring-boot-starter-parent-4.1.0.pom
# 4.1.0 → 200 (존재) / 4.1.0.RELEASE → 404 (없음)
  • 배경: .RELEASE 접미사는 Spring Boot 1.x~2.0 시절 표기의 잔재. 지금은 안 씀.
  • 교훈: 도구(Initializr)가 주는 값도 틀릴 수 있다. 에러 메시지가 원인을 정확히 알려준다.
② Spring Boot 3.x ↔ 4.x 의존성 이름이 다름
Boot 3.xBoot 4.x
웹spring-boot-starter-webspring-boot-starter-webmvc
테스트spring-boot-starter-testspring-boot-starter-webmvc-test

버전을 바꿀 땐 의존성 이름도 같이 확인해야 한다.

③ 포트 충돌 2연속
  • 8080 — nginx가 이미 점유 (404 응답이 nginx 형식이라 눈치챔)
  • 8081 — 예전에 띄워둔 Vite docker 컨테이너가 5173과 함께 점유 중이었음
  • 해결: 8082 사용
  • 확인 명령: netstat -ano | grep :8080 → PID 확인 → 그 PID가 점유한 포트 전체 조회
  • 교훈: 응답이 오는데 내용이 이상하면 "내 앱이 아니라 다른 게 응답 중"일 수 있다.
