1 설계 원칙 — 도메인형 패키지

계층형(controller/, service/, repository/로 먼저 나눔) 대신 도메인형(Package by Feature)을 채택한다. 기능(도메인) 단위로 먼저 묶고, 그 안에서 계층을 나눈다.

구분계층형도메인형 (채택)
1차 분류기술 계층 (controller/service/...)도메인 (work/member/...)
응집도낮음 (한 기능이 여러 폴더에 흩어짐)높음 (한 도메인이 한 폴더)
확장폴더마다 추가패키지 복제로 도메인 추가 (게임 등)

3 도메인별 책임

도메인책임
work작품(애니/게임) 조회·목록·상세. 핵심 도메인
character·genre·studio작품 부속 정보. 작품과 연관(소형 도메인)
member회원 가입·정보 관리
auth로그인·JWT 토큰 발급·갱신 (인증 책임만)
favorite회원의 작품 즐겨찾기 (member ↔ work 연결)
searchElasticsearch 통합 검색·자동완성 (JPA와 별도 모델)
external외부 API(Jikan·RAWG) 수집·적재 (스케줄러)
global설정·보안·예외·공통응답 (횡단 관심사)

4 핵심 설계 결정

① JPA Entity ↔ ES Document 분리
work.domain.Work(MariaDB 원본) 와 search.document.WorkDocument(Elasticsearch 검색용)를 별도 모델로 둔다. 저장과 검색의 책임·스키마가 다르기 때문. (적재 시 Work → WorkDocument 변환·색인)
② auth ↔ member 분리 (SRP)
member는 *회원 정보*, auth는 *로그인·토큰 발급* 책임만. 인증 로직이 회원 도메인을 오염시키지 않게 분리.
③ external — 어댑터 패턴으로 격리
외부 API를 소스별(jikan·rawg)로 어댑터 격리. 마켓/소스 추가 시 어댑터만 추가 (하루님 멀티마켓 API 연동 경험과 동일 패턴). API 정책 변경 영향을 국소화.
④ global — 횡단 관심사 집중
설정·보안필터·예외처리·공통응답을 global에 모아 도메인 패키지는 *비즈니스에만* 집중.
조정 가능
character·genre·studio가 너무 작으면 work 하위로 흡수해도 됨. auth를 member에 합쳐도 동작엔 무방(단 분리가 더 깔끔). 프로젝트 규모 보며 조정.

5 도메인 의존 관계

flowchart TD
    auth["auth (인증)"] --> member["member"]
    favorite["favorite"] --> work["work (핵심)"]
    favorite --> member
    search["search (ES)"] --> work
    external["external (수집)"] --> work
    work --> character["character"]
    work --> genre["genre"]
    work --> studio["studio"]
    global["global (공통·설정·보안)"] -.->|횡단| work

화살표 = 의존 방향. work가 중심이고, 외부수집(external)·검색(search)·즐겨찾기(favorite)가 work를 향한다. 순환 의존이 없도록 단방향 유지.

6 MSA 전환 대비 설계 원칙

지금은 모놀리식으로 시작하되, 도메인 경계를 명확히 해 추후 MSA로 떼어낼 수 있게 설계한다. ("Monolith First" — 처음부터 MSA는 오버엔지니어링)

경계 규칙 (지금부터 지킬 것)

  • 경계 넘는 연관 = ID 참조 — 다른 도메인을 JPA FK(@ManyToOne) 대신 Long workId 같은 ID로 참조 (서비스 분리 시 조인 불가 대비). 단 도메인 내부 연관(Work↔Character)은 FK 허용
  • 도메인 간 통신 = service 인터페이스로만 — 다른 도메인 repository 직접 호출 금지
  • 이벤트 기반 결합 완화 — ApplicationEvent로 느슨하게 → 추후 메시지큐(Kafka 등) 교체 용이
  • 각 도메인 자기 데이터 소유 — 자기 테이블만 접근 (추후 DB 분리 대비)
  • global 공유 최소화 — 공통 모듈이 비대하면 분리 어려움

전환 로드맵

1단계 (현재) 모듈러 모놀리식 — 단일 모듈, 패키지 분리 + 경계 규칙
2단계 한 도메인(예: search) 독립 서비스로 분리 — MSA 첫 경험·면접 어필
3단계 API Gateway · Service Discovery · 메시지큐 · 분산추적 (진짜 MSA)
⚠️ 주의
처음부터 MSA로 만들지 말 것 — 오버엔지니어링·미완성 위험. 모놀리식 완성 후 필요 시 점진 분리.
